## What was learned

### 1. The display copy is not the bottleneck (an earlier claim was wrong)

- `MiniIOMobileFramebuffer: N frames … us each in the driver` reads **1.5 to 1.8 ms per frame** on x15, x19,
  x20, x22 and x26. The 3-thread `memcpy` to LK's framebuffer is cheap. An earlier statement of
  "11 to 19 ms of CPU copy" was wrong.
- The display gets only 10 to 32 frames a second because **CoreAnimation produces them that slowly**.
- On x19 the GL bridge averaged 13 ms per frame. Of that, about 1.5 ms was handing commands on,
  about 2.9 ms was waiting for the GPU, and about 0.9 ms was preparing IOSurface textures. The rest is CPU
  work in CoreAnimation's render thread and the bridge. On x26 it was 19.5 ms per frame.
- The GPU is mostly idle, and clocks are not the limit.

### 2. Where the drawing thread's CPU time goes (x22, `glprof=2000`)

These are the top entries (34.5% of samples). Symbolize with `C:\begonia-private\sh\sym.sh` and `prof.py`.

| Share | Where |
|---|---|
| 9.1% | Kernel calls via `macel.dylib` |
| 8.0% | `surface_changed` in `eagl.c`: hashing copied IOSurfaces on the CPU every frame |
| 6.8% + 3.0% | `panfrost_kmod_bo_make_evictable` / `_unevictable` ioctls (BO cache madvise) |
| 2.8% | `jm_submit_jc` |
| 2.4% + 1.0% | `panfrost_bo_unreference`, `panfrost_bo_mmap` (BO churn) |

`surface_changed` exists only because of the copy path: shared textures are never hashed. The
evictable/unevictable ioctls are overhead that the Mesa BO cache could avoid.

### 3. Text and emoji boxes come from the copy path

- `eagl.c` turns an IOSurface into a texture in one of two ways. **Shared:** the GPU reads the surface
  memory (`hakios_gl_surface_texture` → `glEGLImageTargetTexture2DOES` → Mesa `osmesa_surface_resource`).
  **Copied:** the bridge copies it into a separate texture, then hashes it every frame to spot changes.
- Before this session only `BGRA` surfaces could be shared. Text masks are `A008` (GL_ALPHA) and `LA08`
  (GL_LUMINANCE_ALPHA), so all of them were copied. The boxes are always copied textures.
- The x19 summary showed: "copied because not BGRA bytes: 163 surfaces" (format `0x190a`, up to 256 x 186),
  and "copied because the library refused: 7 surfaces, 24 MB".
- **The bridge's counter is misleading.** A mask that Mesa refuses is counted as "not BGRA bytes",
  because that check comes first in the `why` chain.
- **Mali-G76 (Bifrost, v7) imports linear memory only with 64-byte row stride and offset.**
  See `pan_layout.c: format_minimum_alignment`, and x24's log: `panfrost: rejecting image due to
  unsupported offset or stride alignment`, 12 times. The big refused BGRA surfaces fail the same way;
  for example, 1271 px is 5088 B per row.
- **Most masks cannot be made shareable.** The x26 summary: 600 masks offered, **5 shared**, 352 with rows
  not a multiple of 64, 119 with starts not on 64. The kernel realigned only **8**. Most masks are
  **wrapped client memory** (`IOSurfaceAddress`, CoreAnimation wrapping an image's backing store), whose
  layout belongs to the client.
- So the box bug has to be fixed in the copy path itself. History of attempts there: patch 0007
  (R8/RG8 plus swizzle), and the old 0009/0010 (one mip level at upload, then at every bind; text lasted
  minutes, then boxes again). None held.
- **Next step:** capture a GL trace of one texture that renders as a box (swizzle, base/max level, min filter,
  internal format, contents) instead of patching blind. A "filled box" means alpha is 1 everywhere. That
  fits an incomplete texture, or a lost `(0,0,0,R)` swizzle on an R8 texture.
- The clocks did **not** cause the boxes. Boxes appear at 270 MHz (x8 records, x20) as well as 806 MHz.

### 4. Touch: the real cause and the fix

- The kernel driver was fine on every build: thousands of events, `bad 0`.
- Userland 0009's status line (x23, x24) showed **every touch read was sent**
  (`read 1289 touches 1288 sent 1288`), with the service opened on the first attempt and never closed.
- **Cause:** backboardd sometimes misreads the virtual touch screen (usage page 0, "unexpected digitizer
  usage pair") and never takes it as the main-screen digitizer. Touches are then delivered and ignored.
  The lock button is a different service, so tap-to-wake (which presses the lock button) still worked.
  Whether a boot hits this depends on timing, which is why touch came and went between builds and the
  profilers seemed to matter.
- **Signal:** backboardd sets `TouchDetectionMode` on the service either way, and `QuantizationDPI` only
  when it takes it.
- **Fix:** userland 0011, ported from `upstream/ios-s9plus-exynos/core/userland/src/inject.c` `keep_screen()`.
  If the service is judged but not taken, it is removed and remade, up to 3 times. On x25, backboardd took
  the screen on the first try (`judged 1 taken 1 remakes 0`).
- **Lesson:** the newer reference port in `upstream/ios-s9plus-exynos` had already solved this. Check it
  before debugging input or window-server issues from scratch.
- Touch modes in `inject.c`: `0x1` means touches on, `0x1fe` means display off (a touch-down becomes a lock press
  to wake), and `0x101` was seen after wake.

### 5. Tearing and the display hardware

- **Scan-follow** (`fb_line`, kernel 0013) removed tearing, but it holds each frame's rows until the scan
  passes, so x18 dropped to about 10 to 20 fps. It is still in the kernel and off unless `fb_line=` is given.
- **Research** (the Xiaomi tree at the pinned commit; copies are in the session scratchpad):
  - DISP_OVL0 is at `0x14008000`. Layer address registers: L0 at `0xF40`, L1 at `0xF60`.
    SRC_CON at `0x2C` holds the layer enable bits.
  - MT6785 has **no shadow registers** (`disp_helper.c`), and **addresses are 32-bit only**, so scanout
    buffers must be below 4 GiB. XNU's RAM and all IOSurfaces are above 4 GiB.
  - The panel is almost certainly in video mode.
  - LK's display reservation is `0x7d9b0000 + 0x2250000`, and LK scans out from `0x7e384000`. Three
    1080 x 2340 frames (0x9A4000 each) fit: `0x7d9b0000`, `0x7e384000` and `0x7ed28000`.
  - `boot/xnu_loader.c` already reads and writes these OVL registers from the CPU.
- **x27** (kernel 0015, `fb_flip=1`) triple-buffered in that reservation and wrote the layer address at most
  once per refresh. **It did not boot**, and none of its messages reached the log, so the cause is unknown.
  It was reverted in git (5391a2c) and un-applied by hand in the WSL tree. If it is retried: put it behind
  a boot arg, log before every step, and suspect the one-time `memcpy` from the write-combined boot
  framebuffer, the `ml_io_map_wcomb` mappings, or whether those reservation ranges are really unused.

### 6. Memory

- The loader gives XNU **one block above 4 GiB: 0x1_0000_0000 + 0xB7F00000, about 2.9 GB** of the
  phone's 6 GB. The low 3 GB holds LK, TrustZone/ATF, pstore, the framebuffer and modem regions. XNU's
  arm64 start-up takes one contiguous range, so using more RAM needs kernel support for memory holes.
- Memory is **not** a current problem: x20 had 466 MB free, 1.8 GB available, no compressor use and no jetsam.

## Workflow lessons and gotchas

- **One-shot latch.** The loader runs XNU once per build. It hashes the command line (which includes
  `epoch=`) plus the ADT, and on a match boots the headless serial fallback, which leaves the screen on the
  Redmi logo. **Re-flashing an image that has already run does not start iOS.** Rebuild under a new tag.
- **Early console lines are lost.** launchd's "failed lookup" spam fills the 256 KB ring within minutes,
  even in 60 s sessions. Put diagnostics in **periodic late lines**: the input status every 10 s, and the
  mask summary every 50 masks.
- `touch_lat=1` logs every frame and fills the ring. Use it only briefly.
- **Kernel patches to `MiniIOSurface.cpp` and `MiniIOMobileFramebuffer.cpp` must also go into
  `xnu/files/`.** Add the patch name to the sync list at the end of `tools/prepare_kernel.py`.
- `prepare_kernel.py` never un-applies a patch removed from `patches/`. Reverse-apply it in the WSL tree
  by hand.
- Mesa changes go in `userland/mesa-patches/`. `tools/build_gles_linux.sh` applies each one once.
- Git Bash rewrites `/mnt/c/...` paths passed to `wsl`. Run builds from PowerShell, or set
  `MSYS_NO_PATHCONV=1`. Multi-step WSL commands are most reliable as a script file under the scratchpad.
- Windows has no Python. Patch generation runs `python3 -I` inside WSL.
- `build_all.sh` filters its output, so a userland compile error shows only as a missing feature. Check
  the built library with `grep -c '<new string>' …/userland/obj/libhakios.dylib` and the payload timestamps.
- Bisecting against kept images works. Re-flashing x15 proved touch was a code or timing change, not
  phone state.
