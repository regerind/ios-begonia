## What was wrong, and the fixes (all general)

1. **No pipeline reflection.** The front end answered every `reflection:` with nil; Freeform aborted ("Failed to create
   pipeline reflection object"). Now the runtime's reflection (metal2vulkan reads it off the AIR) goes through the bridge
   (`userland/metal/bridge/begonia_reflection.rs`, `nmb_*_pipeline_reflection2`) and the front end makes MTLArgument /
   MTLBinding / MTLRenderPipelineReflection / MTLComputePipelineReflection of it
   (`userland/metal/frontend_reflection.mm.inc`), with the buffers' **struct layouts** (MTLStructType / MTLStructMember /
   MTLArrayType): SceneKit fills its uniforms member by member and bound nothing for its transforms without them (y39).
2. **No application shader libraries on the system volume.** `sysimage/select-system.py` skips every `.metallib`
   (142 files, 192 MB in the firmware). All are now extracted to `sysimage/metallibs/` (7z from the IPSW's root image);
   the libraries of the applications shown the device, SpriteKit's and SceneKit's are staged in the support image
   (`/redwood/ext/metallib/<bundle id or bundle path>/`), and the plug-in's NSBundle lookups of a `.metallib` fall back
   there. MetalPerformanceShaders (95 MB), CoreImage, VideoToolbox and the rest need the system volume (proposal below).
3. **Buffer mappings torn down under the runtime.** IOKit gives a second mapping of a buffer the same address, and
   PanVK's unmap after every host image copy took the runtime's persistent mapping away; the next texture upload faulted
   (y29/y30). The transport keeps one counted mapping per buffer and no longer narrows its protection
   (`userland/vulkan/native-patches/0001`).
4. **Metal source.** Engines generate shader source at run time. The front end had no `newLibraryWithSource:`; the
   system's own compiler works here (its source-to-AIR half needs no Apple GPU), so the source goes to it and the
   metallib it makes is opened by the runtime (`userland/metal/frontend_source.mm.inc`).
5. **MSAA resolve.** The bridge's render-pass record had no resolve texture, so every resolving pass was refused
   (bridge patch 0001 adds it). Then PanVK's multisampled fragment job faulted on this GPU (JS_STATUS 0x58), so MSAA is
   emulated at one sample by default: multisampled textures are made single-sampled and a resolving attachment draws
   straight into its resolve target. Games draw right, without edge smoothing. `metal_msaa=1` for real MSAA.
6. **A failed GPU job froze its program.** The kernel answered a wait on a failed job "not done" for ever (and never
   freed its buffers). A failed job now counts as ended (`kernel/bsd/dev/begonia_mali_service.c`).
7. **Small ones.** `MTLCommandBuffer.logs` / `errorOptions` (Measure aborted on the unknown selector); console output
   from applications (`metal: NAME[pid]: ...`); the libraries' load addresses for placing a crash; PanVK built for
   Bifrost v7 alone (1 MB less in a full boot image).

## How to build it (all under WSL, on this PC)

    bash tools/build_panvk_linux.sh               # PanVK (upstream/mesa-vulkan @8e87a503; userland/vulkan/patches)
    bash tools/build_metal2vulkan_linux.sh        # the runtime, built for size (M2V_FULL=1: the faster build)
    python3 tools/build_metal_frontend_ios.py --sdk $THEOS/sdks/iPhoneOS16.5.sdk \
        --cc $PWD/upstream/hakios-xnu-kernel/xnu-deps/host/bin/xnu-clang --experimental-mps-stubs
    bash tools/build_gpu_tests_linux.sh           # metal_frontend_test, vulkan_device_test, metal_game_test, sprite/scenekit_test

Images: `auto_build.sh TAG WATCH " metal=1 ..." "SCRIPT" "CLIENTS"` (fifth argument; `y_cycle.sh` takes it fourth). CLIENTS:
program names, `@apps` (every application: an .app in /Applications, the containers or the staged applications; not
SpringBoard, no daemon), `!Name` (not this one). Boot arguments: `metal=1` (required), `metal_msaa=1`, `metal_calls=1` (every
encoder and command-buffer call on the console, first 300), `metal_reflection=0`.

## Proposal (needs the owner's yes): the system volume, with every shader library and games

The boot partition is full (66.5 of 67.1 MB). Everything bigger belongs on the system volume, which lies at userdata +
256 MiB, 2.48 GB, with 476 MB free before the iOS data volume at 3 GiB:

1. Keep `.metallib` in `sysimage/select-system.py` (SKIP_EXT, SKIP_APP_EXT), `KEEP=1 sysimage/unpack.sh` (rootfs.dmg is
   kept now), rebuild the userland (`userland/build.sh`, which makes `system.apfs`): +192 MB.
2. Optionally games: decrypted `.app` bundles in the system's /Applications (system applications are registered at boot;
   code signing is off on this port). About 280 MB of room is left after the libraries.
3. `tools/make_userdata_head.sh` (a sparse image of the first 3 GiB of userdata: nothing at or past the data volume),
   then `fastboot flash userdata out/userdata/head.simg` once. Every boot image built after it takes the new size of
   `system.apfs` for its system extent (`build_userdata_boot.sh`), so the boot image must be rebuilt after it too.

This writes userdata (the system region only), which today's rules do not allow without the owner: it is prepared here,
not done. With it, Photos and the other system applications that need their frameworks' libraries work with Metal, and
MetalPerformanceShaders stops being stubbed.
