# What was learned, 2026-11-19 (builds x28 to x90, p1)

Everything one long working session established about iOS 16.5 on the Redmi Note 8 Pro (begonia, MediaTek
MT6785 / Helio G90T): how the graphics path works, what made it slow, what made the boxes and the tearing, what
fixed them, what did not, the hardware facts measured along the way, and how to test with nobody at the phone.
Organised by subject, not by time. The run-by-run account is `docs/SESSION-2026-11-19b.md`; the session before it
is `docs/SESSION-2026-11-19.md`. Logs are in `C:\begonia-private\logs\xNN-console.txt`.

The hard rule did not change: only the boot and misc partitions are ever written (`flash_tag.sh`). The IMEI
partitions (nvram, nvdata, protect1/2, persist, proinfo, ...) are never touched.

## 1. Results

| | Start (x28) | End (x57 to x90, a build with no extra boot arguments) |
|---|---|---|
| Frame rate during gestures | about 25 fps | 51 to 58 frames in each second |
| Home-screen page swipes | | 75 to 90% of frame intervals under 18 ms; none or 1% over 35 ms |
| Settings scrolling | | 73 to 92% under 18 ms |
| Emoji keyboard over Spotlight | | 64 to 68% under 18 ms, 7 to 14% over 35 ms (the GPU's limit) |
| Tearing | yes | none: 0 torn updates counted by the display driver in every session |
| Black boxes on text and emoji | yes | none: no texture without a picture in tens of thousands checked a session |
| Touch | came and went between boots | taken by backboardd every boot |
| Restart | Redmi logo (one-shot latch) | iOS again, with a `begonia_persist=1` image (p1) |

Nothing was traded for these: wallpaper, resolution, transparency and motion are as iOS has them. The user does not
want any of them reduced, and asked not to touch the wallpaper.

## 2. The graphics path, as it actually is

```
CoreAnimation (backboardd's render thread, bound to an A76)
  -> EAGL bridge          userland/src/eagl.c -> /redwood/lib/libhakios.gl.dylib (userland/patches/*)
  -> OSMesa + Panfrost    Mesa 25.0.7, libOSMesa.8.dylib (userland/mesa-patches/*)
  -> DRM shim             mesa src/hakios-drm/: hakios.drm.c, hakios-native-sync.c (made by tools/prepare_gles_userland.py)
  -> IOKit user client    HakiosMali, iokit/Kernel/begonia.mali.cpp (GENERATED by tools/prepare_gpu_service.py)
  -> job queue            kernel/bsd/dev/begonia_mali_service.c: one thread, one job at a time, polls the GPU
  -> Mali-G76 MC4 (Bifrost, arch v7)
display: MiniIOMobileFramebuffer copies the frame's surface into LK's framebuffer (3 threads, about 1.7 ms),
         behind the panel's scan (kernel patch 0013)
```

- **Surfaces reach the GPU two ways.** *Shared*: Panfrost imports the IOSurface's memory (zero copy). *Copied*: the
  bridge uploads it into its own texture, and must notice later changes itself (it hashes the memory).
- **Panfrost on v7 imports linear memory only with 64-byte row stride and offset.** Research into the Mesa merge
  requests (7653, 19620, 21109) says this is very likely a real hardware limit for sampling too (an R8 image with
  480-byte rows faulted on a G52). So most text masks (CoreAnimation wraps its own image memory, rows of any length)
  stay on the copy path. Do not relax the check.
- **IOSurface seeds** move only when a writer locks a surface for writing. Surfaces of their own changed without the
  seed moving in about 1% of looks; wrapped memory (`methodWrapClientImage`) never did, in tens of thousands.
- **CoreAnimation makes a new display surface for nearly every frame** (seen as "the frames came in surfaces N, N+1,
  ... none twice").
- **CoreAnimation itself is cheap here:** 1 to 2 ms a frame. Almost all of a frame's time was inside GL calls.
- **The GPU's work per frame** on the home screen: about 21 fragment jobs of about 0.6 ms (four or five full-screen
  passes of 1 to 4 ms are 80% of it) and as many vertex/tiler jobs of 70 us: 13 to 14 ms. Tiler and fragment jobs
  cannot overlap: Mesa gives all batches one tiler heap.

## 3. Why it was slow, and what fixed it (measured, in order of effect)

| Cause | Fix | Effect |
|---|---|---|
| The DRM shim took a global mutex on every `drmIoctl` and broadcast a condition at every submit, against its fence worker; the bridge also asked for a fence (a pipe and a sync file) every frame | Mesa 0004 (set the wait callback once), Mesa 0005 (broadcast only to waiters), userland 0023 (no fence per frame) | 60% to 87% of intervals under 18 ms; 49 to 21 us a draw (x43 to x44) |
| Upstream panfrost unmaps every buffer it puts in its cache and maps it again on reuse; here a map is a Mach message, an unmap a `mach_vm_deallocate`, and every page faults again | Mesa 0003: buffers stay mapped while cached, unmapped when freed | map requests 2646 to 19-86 per 5 s; frame 17.2 to 14.4 ms (x36 to x37) |
| The bridge had the GPU copy each new (all-zero) display surface into the frame's target: a full-screen job a frame | userland 0022: a surface whose seed is still 1 is cleared, not copied (`glfill=1` restores) | 87% to 98% (x44 to x45) |
| The kernel cleaned the CPU cache for every whole surface (12.7 MB) a job named, at every submit | `mcs=1` made the default (clean when the seed moved; wrapped memory always) | submit request time halved |
| Closing a buffer waited up to 2 s for its last GPU job, with the driver's lock held | deferred free in the HakiosMali client (`reapBuffers()`) | `glDeleteTextures` over 4 ms: 191 times to once in ~35 s (x56 to x57) |
| Smaller ones | Mesa 0002 (no madvise ioctls; the kernel only answered "retained"), Mesa 0004's local answer to buffer-idle looks, userland 0015 (no hashing of wrapped memory) | a few % each |

**What the slowness was not:**
- *Clocks or voltages.* Already at the stock top (section 7). Raising them further is neither possible nor needed.
- *Battery throttling.* There is no fuel-gauge driver and no Apple power controller (CLPC) here; nothing in iOS can
  change a clock. The status bar's 100% (userland 0013) is cosmetic.
- *Redundant GL state calls.* About one call a frame set what was already set; a state cache would gain nothing.
- *CoreAnimation, or memory bandwidth from a low DRAM clock* (section 7).
- *Where the GPU job thread runs.* Binding it to an A55 (x34) changed nothing (kept, harmless).
- An early reading that "the drawing thread is blocked most of the time" was wrong: that session was mostly idle.

**Tried and dropped:** drawing straight into the display surface (`glblit=0`: fragment jobs slower, 600 to 700 us);
no read-back under the frame's final copy (Mesa 0006, reverted: no gain within the noise); pacing the window server
from the panel's scan (`fb_vsync_scan=1`, kernel 0017: one session better, one worse, so off by default).

## 4. The black boxes on text and emoji

- **Cause:** `eagl.c` tracked the textures that are IOSurfaces in a table of 256. When it was full,
  `-texImageIOSurface` gave up and the texture stayed with no storage. CoreAnimation drew with it anyway, and a
  texture without storage samples as opaque black. The emoji keyboard and fast scrolling create many such textures.
  The log said it outright: "more textures with IOSurfaces than there is room for" (298 times in x22, 112 in x49).
- **Fix:** userland 0025 makes the table 2048 entries, with a lookup hint so lookups stay short.
- **What found it:** checking *every* bound texture at draw time (userland 0024: 438 with no storage, all
  CoreAnimation's) and screenshots printed into the log (whole columns of the emoji grid black, x48).
- **What it was not:** texture state. Swizzles, mip levels, min filters were checked about 3,000 times a session from
  x30 on and never wrong. Every earlier attempt (R8 masks with swizzle, single mip level, sharing masks, 64-byte rows)
  treated textures that did have a picture.

## 5. Tearing

- The display driver already knew how to write each part of the frame behind the panel's scan (`fb_beam`). It lacked
  a line counter for this SoC: DISP_RDMA0's OUT_LINE_CNT at `0x1400b12c` counts the scan (kernel 0013, now built in).
- It starts 20 s after the driver (`fb_beam_wait=`), measures the scan (16.603 ms, 2340 lines) and counts parts written
  across the scan line ("shares of the rows, us each/torn/close"): 0 torn in every session since.
- Cost: intervals spread a little (with it, most of the rest fall between 18 and 26 ms; without it, x45 had 98% under
  18 ms but tears). Every frame still gets a refresh of its own. `fb_line=0` turns it off.
- Real page flipping on DISP_OVL0 (an earlier attempt, x27) did not boot and is not needed for tear-free output.

## 6. Touch, buttons, and the restart that stayed on the Redmi logo

- **Touch:** backboardd sometimes misreads the virtual touch screen and never takes it. It sets `TouchDetectionMode` on
  the service when it judges it and `QuantizationDPI` only when it takes it. Userland 0011 remakes a screen that was
  judged and not taken; 0019 also one that was never judged within 15 s (x32: "has not decided"). The input status
  line now puts its counters first (the logger's line length cut them off before).
- **Buttons "not working":** at a test session's deadline (`begonia_watch=60`) the supervisor's reset makes the PMIC
  report the power key held down, so the last ~25 s of every session had the lock button "held". Before the deadline
  buttons worked (17 presses in x35). `begonia_buttons.c` ignores the power key from 6 s before the deadline.
- **Restart hung on the Redmi logo:** the loader (`boot/xnu_loader.c`, built with `XNU_FORCE_TEST`) runs iOS once per
  image. It hashes the payload's command line (with its `epoch=`) and device tree; a matching latch in RAM
  (0x4d0df108) or a log capture in the mirror (0x1b7e00000) makes every later boot chain the fallback kernel: TWRP,
  headless, with a serial gadget, and the Redmi logo on screen. That was deliberate for testing, so a broken image
  always came back to something recoverable.
- **Fix (p1, commit 28ebf74):** `begonia_persist=1` in the payload's command line makes the loader start iOS on every
  boot, warm or cold, with no session deadline. Ways out: **Power + Volume-Down at power-on** (LK's fastboot, before
  our code runs), or **Volume-Up held while the logo shows** (the loader then chains the serial fallback; it reads the
  keypad at 0x10010004 and ignores an all-zero, unclocked keypad). Build it with
  `auto_build.sh TAG 0 " begonia_persist=1" ""`. Test images keep the one-shot behaviour.
- **The first GPU job of every boot failed** (JS_STATUS 0x42 after 400 ms), and the kernel reset the GPU: the address
  space's attributes and translation configuration were only written by the recovery. `flush_tables()` now writes
  them with the table (commit 8031461).

## 7. Hardware facts measured

| | |
|---|---|
| CPU | XNU processors 0-4 are Cortex-A55, 5 and 6 the A76s (MPIDR 0x600, 0x700); 0x100 is the loader's supervisor core. The drawing thread is bound to 6 (`gl_cpu`), SpringBoard's main thread to 5 |
| CPU clocks | A55 2000 MHz at 1.031 V, A76 2002 MHz at 1.100 V, interconnect 1400 MHz: the MT6785 stock top (the G90T table allows the A76 2050 MHz at 1.119 V). Set once at boot by `begonia_perf.c`; nothing changes them after. `kern.begonia_clocks` reads them back |
| GPU | Mali-G76 MC4, 806 MHz at 781.25 mV core, 881.25 mV memory rail: the G90T's stock top |
| DRAM | LPDDR4X at 4264 Mbps, shuffle level 0, the top rate (read from the DDR PHY's PLL, `begonia_dram_probe=1`). DVFSRC is not driven by anyone here, so it stays where the boot loader left it |
| Panel | 1080 x 2340, video mode, scan 16.603 ms; the window server's timer is 1/60 s (16.667 ms), so they drift past each other every few seconds |
| Display | DISP_OVL0 0x14008000 (layer addresses L0 0xF40, L1 0xF60, 32-bit only, no shadow registers); DISP_RDMA0 line counter 0x1400b12c; LK's framebuffer reservation 0x7d9b0000 + 0x2250000 |
| Memory | XNU gets one block above 4 GiB, 0x1_0000_0000 + 0xB7F00000 (about 2.9 GB of the 6 GB). Not a limit so far |
| Keys | KPD_MEM 0x10010004: bit 0 Volume-Up, bit 1 Volume-Down, low when pressed; the power key is the PMIC's TOPSTATUS (0x2a) bit 1 over PWRAP |

## 8. Testing with nobody at the phone

All in `C:\begonia-private\sh\`, run from Git Bash; see the memory note "unattended test tooling" too.

- **One cycle:** `auto_cycle.sh TAG " boot args" /c/begonia-private/sh/SCRIPT.txt` builds (WSL), flashes, waits for
  the serial fallback, pulls the log and prints the summary (`auto_check.sh`). About 4 minutes; run it in the background.
- **Scripted touches:** `tools/make_ui_support.py --touch-script "STEPS ; STEPS"` (passed as `auto_build.sh`'s fourth
  argument). Each `;` part is one `rwtouch` started at the beginning of the session, so each begins with its own
  `wait SECONDS`; init runs at most 63 words a line. `notify com.hakios.unlock` unlocks. Scripts kept:
  `auto_script.txt` (home-screen pages), `auto_script_settings.txt` (Settings), `auto_script_box.txt` (Spotlight,
  emoji key at 0.09 0.945, fast scrolling).
- **Screenshots in the log:** `fb_shot=SECONDS` (`fb_shot_gap`, `_n`, `_step`, `_top`, `_bottom`; kernel 0015), then
  `shot.py LOG PREFIX` makes greyscale PNGs.
- **The measure:** the display driver's histogram "from one frame to the next" (`auto_sum.sh` prints INTERVALS). Not
  frames per 5 s, which counts the pauses between gestures. Runs of the same build differ by 6 to 10 points.
- **Profiling:** `glprof=2000` (sampling profiler; userland 0020 adds a flat profile by code location and library),
  symbolised with `sym.sh`, `prof.py`, `flat.py`. `glslow=4000` logs every GL call over 4 ms. The bridge's summary
  (every 200 frames) has time inside GL calls against CoreAnimation's own, the twelve costliest calls, draw split,
  hashing cost, redundant calls, clocks. `mcp=1`: kernel cache cleaning and every GPU request by kind, count and time.
- **Crashes:** kernel 0016 keeps a fatal exception or abort of backboardd/SpringBoard in the notes, which are then said
  again with every 5 s GPU report; `ustacks=SpringBoard ustacks_at=45 ustacks_ms=8000 ustacks_threads=1` prints
  SpringBoard's main-thread stack every 8 s.
- **Logs:** the serial fallback has no `/dev/mem`; the console is `/sys/fs/pstore/console-ramoops-2` after
  `mount -t pstore pstore /sys/fs/pstore`, pulled as base64 over COM4 (`serial.ps1`). The ring is 256 KB: about 20 s of
  a busy session with the profiler on, about a minute without. Userland lines arrive doubled and interleaved; kernel
  printf lines are clean.

## 9. Gotchas that cost time

- **One-shot latch:** re-flashing an image that has run boots the fallback (Redmi logo); rebuild under a new tag.
- **Fastboot on this PC:** the device appears as 18d1:d00d; `usbipd attach --wsl --hardware-id 18d1:d00d`, then
  `fastboot` inside WSL. It can be listed and briefly not attachable while it enumerates; try again.
- **`build_all.sh` / `auto_build.sh` hide userland and Mesa compile errors**: check new strings are in the built
  library (`grep -c`) and its timestamp. The kernel's error check covers `begonia_*.c` only; look at `/root/kbuild.log`.
- **`begonia.mali.cpp` is generated** by `tools/prepare_gpu_service.py`: edit there, not in the tree.
- **Kernel patches on one file must not touch each other's hunks:** `prepare_kernel.py` decides "already applied" by a
  reverse check and stops. Change the earlier patch itself, and keep the WSL tree and `xnu/files` in step.
- **`tools/make_gles_support.py --ui` rewrote `rc.jobs`** and dropped scripted touches (fixed: it keeps rwtouch lines).
- **`systrace=1` traces every failing system call** and fills the log in seconds; the crash note works without it.
- **The bridge's `say()` lines are at most 1024 bytes;** the input status line's counters were cut off at the end.
- **Writing helper scripts:** shell heredocs in this environment turned `\\n` inside Python strings into real
  newlines; write such files with the editor instead. Git Bash rewrites `/mnt/c/...` arguments to `wsl`
  (`MSYS_NO_PATHCONV=1`). Do not edit a script while a background cycle is using it.
- **A smaller library is not always a broken build:** `libhakios.gl.dylib` shrank 200 KB once because the compiler
  stopped inlining a grown `eagl_enter` into a thousand generated wrappers.
- **Reading a profile:** `dladdr` names the nearest exported symbol, so a bucket labelled `mach_vm_deallocate` was
  really `__psynch_mutexwait` (lock contention). Symbolise against the unstripped libOSMesa.

## 10. Still open

- **The window server, about one session in ten:** three sessions had backboardd and SpringBoard start anew in the
  middle (x46, x52, x61) and one had the screen stand still while touches were delivered (x75). The cause is not known;
  the capture above is in place and the last 29 sessions were clean.
- **GPU-bound heavy scenes** (the emoji keyboard: 7 to 14% of intervals over 35 ms). Clocks and memory are at the top,
  so the way forward is less GPU work per frame (full-screen passes around blurs, the frame's final copy).
- **`mcs=1` trusts the IOSurface seed** for cache cleaning; nothing stale was seen in any screenshot. `mcs=0` if it is.
- **`fb_vsync_scan=1`** needs more sessions to judge.
- **p1 has not been checked on the phone yet:** it was flashed at the end of the session. Check that a restart from
  iOS comes back to iOS, and that Power + Volume-Down still reaches fastboot.

|---|---|---|
